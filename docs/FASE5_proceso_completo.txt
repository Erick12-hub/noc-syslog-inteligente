 2. CONCEPTOS
================================================================================

 2.1 Integración continua (CI)
   Un servidor ejecuta automáticamente las pruebas cada vez que se sube código.
   Ventajas:
   - Demuestra que el proyecto funciona en un equipo LIMPIO (no solo en el PC
     del estudiante, que puede tener algo instalado que el proyecto no declara).
   - Detecta errores antes de publicar: un Pull Request con pruebas en rojo no
     debería fusionarse.
   GitHub Actions es la CI integrada en GitHub. Lee los archivos YAML de la
   carpeta .github/workflows/.

 2.2 Versionado semántico (SemVer): MAYOR.MENOR.PARCHE
   0.1.0  alfa: primera versión funcional (Fase 2)
   0.2.0  MVP: nuevas funciones compatibles (Fases 3 y 4)
   1.0.0  versión madura (Corte 3)
   "0.x" indica que el proyecto aún está en desarrollo inicial.
   "-dev" (0.2.0-dev) indica una versión EN CONSTRUCCIÓN; se quita al publicar.

 2.3 Pull Request (PR)
   Una solicitud para fusionar una rama en otra (develop -> main), que GitHub
   muestra con todos los commits, los archivos cambiados y el resultado de las
   pruebas. Es el punto de REVISIÓN antes de publicar.

 2.4 Etiqueta (tag) anotada
   Un nombre fijo para un commit concreto ("v0.2.0" = a68582e). La anotada
   (git tag -a) guarda autor, fecha y mensaje: es la forma oficial de marcar
   una versión. Una etiqueta no se mueve aunque lleguen commits nuevos.

 2.5 Release
   La página de GitHub que presenta una etiqueta como versión publicada: título,
   notas y descarga del código (zip y tar.gz). Es lo que el docente revisa como
   "release o etiqueta v0.2.0".

 4.1 .github/workflows/pruebas.yml
--------------------------------------------------------------------------------
  +--- .github/workflows/pruebas.yml -----------------------------------------
  |   1 | # Integración continua (CI): GitHub ejecuta las pruebas automáticas en cada
  |   2 | # push y en cada Pull Request. Si una prueba falla, el commit queda marcado en rojo.
  |   3 | name: Pruebas
  |   4 | 
  |   5 | on:
  |   6 |   push:
  |   7 |     branches: [main, develop]
  |   8 |   pull_request:
  |   9 |     branches: [main]
  |  10 | 
  |  11 | permissions:
  |  12 |   contents: read          # solo lectura: el flujo no necesita escribir en el repositorio
  |  13 | 
  |  14 | jobs:
  |  15 |   pytest:
  |  16 |     runs-on: ubuntu-latest
  |  17 |     strategy:
  |  18 |       matrix:
  |  19 |         python-version: ["3.12", "3.14"]
  |  20 |     steps:
  |  21 |       - name: Descargar el código
  |  22 |         uses: actions/checkout@v4
  |  23 |       - name: Instalar Python ${{ matrix.python-version }}
  |  24 |         uses: actions/setup-python@v5
  |  25 |         with:
  |  26 |           python-version: ${{ matrix.python-version }}
  |  27 |       - name: Instalar dependencias (versiones fijadas)
  |  28 |         run: python -m pip install -r requirements.txt
  |  29 |       - name: Ejecutar las pruebas
  |  30 |         # Sin .env: las pruebas usan valores por defecto y una base temporal.
  |  31 |         run: python -m pytest -v
  +-----------------------------------------------------------------------------

 EXPLICACIÓN
   L3  name: el nombre que aparece en la pestaña Actions y en la insignia.
   L5-9  on: CUÁNDO se ejecuta: en cada push a main o develop y en cada
          Pull Request hacia main.
   L11-12  permissions: solo lectura. Principio de mínimo privilegio: el flujo
          no puede modificar el repositorio aunque alguien alterara un paso.
   L16  runs-on: una máquina virtual Ubuntu nueva y limpia en cada ejecución.
   L17-19  matrix: el mismo trabajo dos veces, con Python 3.12 y 3.14
          (de ahí los 2 jobs y los 4 checks del Pull Request).
   L22  checkout: descarga el código del commit que se está probando.
   L24  setup-python: instala la versión de Python de la matriz.
   L28  Instala EXACTAMENTE las versiones fijadas en requirements.txt.
   L31  Ejecuta las 76 pruebas. Si una falla, el commit queda en rojo.
          No necesita .env: las pruebas usan valores por defecto y una base
          temporal. Así la CI no requiere ningún secreto.

 9. PREGUNTAS PROBABLES DE SUSTENTACIÓN (CON RESPUESTA)
================================================================================
 P: ¿Para qué sirve GitHub Actions en tu proyecto?
 R: Ejecuta las 76 pruebas en un equipo limpio en cada push y Pull Request.
    Demuestra que el proyecto se instala y funciona solo con requirements.txt,
    no únicamente en mi PC.

 P: ¿Por qué dos versiones de Python?
 R: Para comprobar compatibilidad: 3.14 es la que uso y 3.12 es una versión
    anterior todavía muy usada. Si algo dependiera de la versión, se vería.

 P: ¿Qué diferencia hay entre etiqueta y release?
 R: La etiqueta es la marca en Git de un commit (v0.2.0 = a68582e). La release
    es la página de GitHub que publica esa etiqueta con notas y descargas.

 P: ¿Por qué un Pull Request si trabajas solo?
 R: Porque es el punto de control antes de publicar: muestra todos los cambios
    y el resultado de las pruebas, y deja registro de qué entró en la versión.

 P: ¿Por qué merge commit y no squash?
 R: Squash juntaría los 13 commits en uno y se perdería la evidencia del avance
    progresivo que pide la guía. El merge commit conserva todos.

 P: ¿Cómo sabes que la release corresponde al código probado?
 R: La etiqueta apunta a a68582e (verificado con git rev-list), el merge del PR
    cuyos 4 checks pasaron; la release muestra ese mismo commit con ✓.
