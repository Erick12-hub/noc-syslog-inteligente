 2. CONCEPTOS QUE NECESITAS ENTENDER ANTES DEL CÓDIGO
================================================================================

 2.1 Evento vs. incidente
   EVENTO     = un mensaje Syslog que llegó ("Gi0/0/2 cambió a down").
                Llegan cientos; la mayoría son informativos.
   INCIDENTE  = un PROBLEMA que alguien debe atender y cerrar ("el enlace del
                core está caído"). Tiene responsable, estado, seguimiento y
                resolución. Un incidente puede agrupar muchos eventos.
   En ITIL (buenas prácticas de gestión de servicios TI) un incidente es
   "una interrupción no planificada o una reducción de calidad de un
   servicio". El NOC existe para detectar incidentes y cerrarlos rápido.

 2.2 ¿Quién decide la severidad y quién decide la confianza?
   - La SEVERIDAD la escribe quien envía el mensaje (va dentro del PRI).
     El NOC la LEE, no la inventa.
   - La CONFIANZA la decide el NOC: compara la IP real del paquete con el
     inventario (lista permitida). Un mensaje puede decir "soy severidad 0"
     y aun así venir de una fuente no autorizada.
   Por eso la regla de incidentes usa LAS DOS condiciones:
       severidad 0-3 (lo que dice el mensaje)  Y  fuente autorizada (lo que
       verifica el NOC).

 2.3 Política de severidades (tabla severities)
   La tabla severities (creada en la Fase 1) tiene la columna
   creates_incident. Las severidades 0 Emergency, 1 Alert, 2 Critical y
   3 Error tienen creates_incident = 1. Así la política está en DATOS y no
   escondida en el código: si mañana se decide que Warning (4) también crea
   incidentes, se cambia una fila, no el programa.

 2.4 Correlación
   Correlacionar = reconocer que varios eventos son el MISMO problema.
   Clave de correlación = "id_del_equipo|código_del_evento"
       ejemplo:  "1|LINK-3-UPDOWN"
   Si llega otro LINK-3-UPDOWN del equipo 1 y ya hay un incidente ABIERTO con
   esa clave, se suma a ese (event_count + 1) en vez de abrir otro.
   Diferencia con la deduplicación de la Fase 2:
       Deduplicación -> mensajes IDÉNTICOS (misma huella) en 60 s: se guarda
                        UN evento con dup_count.
       Correlación   -> eventos DISTINTOS del mismo tipo y equipo, sin límite
                        de tiempo mientras el incidente esté abierto: se
                        guardan TODOS los eventos, pero cuentan en UN
                        incidente.
   Ejemplo: caen Gi0/0/2, Te0/1/0 y Se0/2/0 del mismo router: son 3 eventos
   distintos (no se deduplican) pero 1 solo incidente con 3 eventos.

 2.5 Máquina de estados
   Es una forma de programar algo que pasa por estados con transiciones
   permitidas. Se define con un diccionario:
       abierto     -> asignado, en_progreso, cerrado
       asignado    -> en_progreso, cerrado
       en_progreso -> cerrado
       cerrado     -> (ninguno: estado final)
   Cualquier otra transición (por ejemplo, de en_progreso volver a
   asignado) se rechaza con el código HTTP 409 "Conflict".

 2.6 Códigos HTTP que usa la API de incidentes
   200 OK            la acción se hizo
   201 Created       se creó algo nuevo (incidente o nota)
   400 Bad Request   datos inválidos (título corto, sin resolución, etc.)
   404 Not Found     el incidente o el evento no existe
   409 Conflict      la acción choca con el estado actual (transición no
                     permitida, incidente cerrado, evento que ya tiene
                     incidente abierto)

 2.7 Dashboard y KPI
   KPI (Key Performance Indicator, indicador clave) = un número que resume el
   estado. El dashboard consulta /api/dashboard cada 15 segundos (polling) y
   redibuja. Las gráficas se hacen con <div> cuyo ancho o alto es un
   porcentaje del valor máximo: no se necesita ninguna librería externa
   (menos dependencias = menos superficie de ataque).

 2.8 Tiempo en UTC
   Todas las fechas se guardan en UTC ("...Z"). El navegador las convierte a
   la hora de Colombia (UTC-5) al mostrarlas. Así se pueden comparar eventos
   de equipos en distintas zonas horarias sin confusiones.

 3. RECORRIDO: DE UN EVENTO CRÍTICO A UN INCIDENTE CERRADO
================================================================================

   Router (192.0.2.1) envía:  <187>... %LINK-3-UPDOWN: Interface Gi0/0/2 ... down
                              PRI 187 -> severidad 3 (Error)
          |
          v
   app/ingest.py  ingest()   pasos 1 a 7 de la Fase 2 (parsear, inventario,
          |                  lista permitida, prompt injection, deduplicar,
          |                  guardar, auditar)
          v
   PASO 8  app/incidents.py  auto_incident_from_event()
          |
          +-- ¿Fuente autorizada?  NO  -> no hay incidente (fin)
          +-- ¿severities.creates_incident = 1?  NO -> no hay incidente (fin)
          +-- clave = "1|LINK-3-UPDOWN"
          +-- ¿Incidente ABIERTO con esa clave?
          |       SÍ -> event_count + 1, severidad = la más grave  ("correlacionado")
          |       NO -> crea incidente con título del SISTEMA:
          |             "LINK-3-UPDOWN en SIM-CORE-RTR01"     ("NUEVO")
          v
   Consola del receptor:  ... -> incidente #1 NUEVO
          |
          v
   Dashboard (/)          KPI "Incidentes abiertos" sube a 1
          |
          v
   Página /incidentes     el operador abre el incidente:
       1. Asignar a "Erick"            abierto     -> asignado
       2. Marcar en progreso           asignado    -> en_progreso
       3. Nota: "Se revisa la fibra"   (seguimiento)
       4. Cerrar con resolución        en_progreso -> cerrado
          |
          v
   incident_notes  (5 notas con autor y fecha)  +  audit_log (cada acción)

 6.1 app/schema.sql y app/db.py  (migración de incidentes)
--------------------------------------------------------------------------------
 La tabla incidents existía desde la Fase 1. Se le agregan 3 columnas:

  +--- app/schema.sql (fragmento, L83-106) -----------------------------------
  |  83 | CREATE TABLE IF NOT EXISTS incidents (
  |  84 |     id           INTEGER PRIMARY KEY AUTOINCREMENT,
  |  85 |     title        TEXT NOT NULL,
  |  86 |     description  TEXT,
  |  87 |     severity     INTEGER NOT NULL CHECK (severity BETWEEN 0 AND 7),
  |  88 |     status       TEXT NOT NULL DEFAULT 'abierto'
  |  89 |                  CHECK (status IN ('abierto', 'asignado', 'en_progreso', 'cerrado')),
  |  90 |     assigned_to  TEXT,
  |  91 |     device_id    INTEGER REFERENCES devices(id) ON DELETE SET NULL,
  |  92 |     event_id     INTEGER REFERENCES syslog_events(id) ON DELETE SET NULL,
  |  93 |     resolution   TEXT,                   -- obligatoria al cerrar
  |  94 |     created_by   TEXT NOT NULL,
  |  95 |     created_at   TEXT NOT NULL,
  |  96 |     updated_at   TEXT NOT NULL,
  |  97 |     closed_at    TEXT,
  |  98 |     is_simulated INTEGER NOT NULL DEFAULT 0 CHECK (is_simulated IN (0, 1)),
  |  99 |     -- Fase 3: correlación. Eventos del mismo equipo y mismo tipo se suman al
  | 100 |     -- incidente abierto en vez de crear uno nuevo por cada evento.
  | 101 |     correlation_key TEXT,
  | 102 |     event_count     INTEGER NOT NULL DEFAULT 1,
  | 103 |     last_event_at   TEXT
  | 104 | );
  | 105 | 
  | 106 | CREATE INDEX IF NOT EXISTS idx_incidents_status ON incidents(status);
  +-----------------------------------------------------------------------------

 EXPLICACIÓN
   status ... CHECK (status IN (...)): la base de datos misma rechaza un
        estado que no sea uno de los 4. Es una segunda barrera además de la
        validación en Python.
   resolution: queda vacía hasta el cierre; el código exige llenarla.
   correlation_key: la clave "equipo|código" (ver 2.4).
   event_count: cuántos eventos se sumaron a este incidente. DEFAULT 1 =
        el que lo creó.
   last_event_at: fecha del último evento correlacionado.
   CREATE INDEX ... ON incidents(status): un índice es como el índice de un
        libro: acelera las consultas que filtran por estado (la lista de
        "abiertos" se pide cada 15 s desde el dashboard).

 ¿Por qué hace falta una MIGRACIÓN? CREATE TABLE IF NOT EXISTS no modifica
 una tabla que YA existe. En el PC del estudiante la tabla incidents ya
 existía (vacía) desde la Fase 1, así que las columnas nuevas se agregan con
 ALTER TABLE:

  +--- app/db.py (fragmento, L63-86) -----------------------------------------
  |  63 | MIGRATIONS = [
  |  64 |     ("syslog_events", "mnemonic", "TEXT"),
  |  65 |     ("syslog_events", "flags", "TEXT"),
  |  66 |     ("incidents", "correlation_key", "TEXT"),
  |  67 |     ("incidents", "event_count", "INTEGER NOT NULL DEFAULT 1"),

================================================================================
 12. PREGUNTAS PROBABLES DE SUSTENTACIÓN (CON RESPUESTA)
================================================================================

 P: ¿Cuándo crea el NOC un incidente automáticamente?
 R: Cuando llega un evento de severidad 0 a 3 (Emergency, Alert, Critical,
    Error) desde una fuente AUTORIZADA del inventario. La política está en
    la tabla severities (creates_incident).

 P: Si un equipo desconocido envía una "emergencia" (severidad 0), ¿qué pasa?
 R: El evento se guarda, se marca fuente_no_autorizada y se audita, pero NO
    crea incidente. La severidad la escribe quien envía; la confianza la
    decide el NOC.

 P: ¿Qué diferencia hay entre deduplicar y correlacionar?
 R: Deduplicar agrupa mensajes IDÉNTICOS en 60 s en un solo evento.
    Correlacionar suma eventos DISTINTOS del mismo equipo y código a un mismo
    incidente abierto. Tres interfaces caídas = 3 eventos, 1 incidente.

 P: ¿Por qué el título del incidente no usa el texto del log?
 R: Porque el log es un dato no confiable. Si un atacante escribe
    instrucciones para una IA en un log, no deben llegar a un título que
    leerán personas o asistentes. El sistema arma el título con el código y
    el equipo; si detecta inyección, usa un título neutro.

 P: ¿Qué es la máquina de estados y por qué se valida en el servidor?
 R: Define qué cambios de estado se permiten (abierto -> asignado ->
    en_progreso -> cerrado). Se valida en el servidor porque la interfaz se
    puede saltar llamando a la API directamente.

 P: ¿Por qué no se puede modificar un incidente cerrado?
 R: Es un registro histórico para auditoría. Si el problema vuelve, se abre
    un incidente nuevo (la correlación solo usa incidentes abiertos).

 P: ¿Por qué la resolución es obligatoria?
 R: Para que quede el conocimiento (causa y solución) y la trazabilidad.
    Sin ella, un incidente podría cerrarse sin haberse resuelto.

 P: ¿Por qué el dashboard se actualiza cada 15 s y no en tiempo real?
 R: Polling cada 15 s es simple, suficiente para un NOC de laboratorio y no
    satura el servidor. En producción se podría usar WebSockets o
    Server-Sent Events.

 P: ¿Qué es un código HTTP 409?
 R: "Conflict": la petición es válida pero choca con el estado actual
    (transición no permitida, incidente cerrado, evento con incidente abierto).

 P: ¿Por qué una migración y no borrar la base?
 R: Para conservar los datos existentes. ALTER TABLE agrega las columnas
    nuevas; _migrate() revisa antes si ya existen (idempotente).
