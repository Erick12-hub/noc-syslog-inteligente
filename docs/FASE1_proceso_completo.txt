      -> El tag v0.1.0 se pondrá al cerrar la Fase 2.
   c) La captura E02 pide "rama de desarrollo".

   d) Requisitos, historias y diagramas se califican (1.00), pero el prompt
      no los producía.
      -> Se escribieron en la Fase 1, antes del código funcional.

 2.3 Decisiones técnicas
   | Decisión              | Alternativa | Por qué                                 |
   |-----------------------|-------------|-----------------------------------------|
   | Flask                 | FastAPI     | Sin dependencias compiladas; instala    |
   |                       |             | sin problemas en Python 3.14 / Windows; |
   |                       |             | más fácil de explicar                   |
   | SQLite                | MySQL/Postg.| Viene con Python, un solo archivo,      |
   |                       |             | sin servidor; suficiente para el MVP    |
   | Puerto UDP 5514       | 514         | Puertos < 1024 exigen administrador     |
   | Fechas en UTC ISO8601 | Hora local  | Correlación entre equipos; con NTP      |
   | IP RFC 5737           | IP privadas | Garantiza que no son IP de producción   |
   | 127.0.0.1             | 0.0.0.0     | La app no queda expuesta a la red       |

--------------------------------------------------------------------------------
 5.1 requirements.txt  -  Dependencias del proyecto
--------------------------------------------------------------------------------

  +--- requirements.txt ------------------------------------------------------
  |   1 | Flask==3.1.3
  |   2 | python-dotenv==1.2.4
  |   3 | pytest==9.1.1
  +-----------------------------------------------------------------------------

 EXPLICACIÓN
   L1  Flask: framework web. Recibe peticiones HTTP, define rutas (/api/...)
       y devuelve respuestas (JSON o HTML).
   L2  python-dotenv: lee el archivo .env y carga sus valores como variables
       de entorno, para no escribir configuración ni secretos en el código.
   L3  pytest: ejecuta las pruebas automáticas (se usa desde la Fase 2).
   "==" fija la versión exacta probada en el equipo. Con ">=" cada
   instalación podría traer versiones distintas y romper el proyecto.
   Instalación:  > python -m pip install -r requirements.txt


--------------------------------------------------------------------------------

--------------------------------------------------------------------------------

  +--- .gitignore ------------------------------------------------------------
  |   1 | # --- Secretos: NUNCA se suben ---
  |   2 | .env
  |   3 | *.pem
  |   4 | *.key
  |   5 | secrets/
  |   6 | 
  |   7 | # --- Base de datos local (se regenera con manage.py) ---
  |   8 | data/*.db
  |   9 | data/*.db-journal
  |  10 | 
  |  11 | # --- Entorno virtual de Python ---
  |  12 | .venv/
  |  13 | venv/
  |  14 | 
  |  15 | # --- Archivos generados por Python ---
  |  16 | __pycache__/
  |  17 | *.py[cod]
  |  18 | .pytest_cache/
  |  19 | 
  |  20 | # --- Editores y sistema operativo ---
  |  21 | .vscode/
  |  22 | .idea/
  |  23 | Thumbs.db
  |  24 | Desktop.ini
  |  25 | .DS_Store
  +-----------------------------------------------------------------------------

 EXPLICACIÓN
   L1-5    Secretos: .env (configuración real), *.pem y *.key (claves
           privadas/certificados) y la carpeta secrets/. Es un CONTROL DE
           SEGURIDAD: cumple "no se aceptan credenciales, tokens ni claves
           visibles en GitHub".
   L7-9    data/*.db: la base de datos local. Contiene datos de operación y
           se regenera con "python manage.py init-db --seed".
   L11-13  .venv/: el entorno virtual pesa mucho y depende de cada equipo;
           cada persona lo crea con requirements.txt.
   L15-18  __pycache__ y *.pyc: archivos compilados que Python genera solo.
   L20-25  Archivos de editores (VS Code, PyCharm) y del sistema operativo.
   Verificación: "git status" no mostró .env, .venv ni noc.db.


--------------------------------------------------------------------------------
 5.3 .env.example  -  Plantilla de configuración
--------------------------------------------------------------------------------

  +--- .env.example ----------------------------------------------------------
  |   1 | # Copie este archivo como .env y ajuste los valores.
  |   2 | # El archivo .env NO se sube a GitHub (está en .gitignore).
  |   3 | 
  |   4 | # Clave de sesión de Flask. Genere una con:
  |   5 | #   python -c "import secrets; print(secrets.token_hex(32))"
  |   6 | SECRET_KEY=cambiar_por_un_valor_aleatorio
  |   7 | 
  |   8 | # Ruta de la base de datos SQLite
  |   9 | DATABASE_PATH=data/noc.db
  |  10 | 
  |  11 | # Receptor Syslog UDP (5514 evita requerir permisos de administrador)
  |  12 | SYSLOG_HOST=127.0.0.1
  |  13 | SYSLOG_PORT=5514
  |  14 | 
  |  15 | # Operador por defecto que aparece en la auditoría
  |  16 | DEFAULT_OPERATOR=operador_noc
  +-----------------------------------------------------------------------------

 EXPLICACIÓN
   Es la plantilla PÚBLICA: documenta qué variables existen, sin valores
   reales. Cada persona la copia como .env (privado) y la ajusta.
   L4-6    SECRET_KEY: Flask la usa para firmar las sesiones. Se genera
           aleatoria con el comando de la línea 5. Nunca se publica.
   L8-9    DATABASE_PATH: dónde se guarda el archivo SQLite.
   L11-13  SYSLOG_HOST/PORT: dirección del receptor Syslog (Fase 2).
           127.0.0.1 = solo este equipo; 5514 en lugar de 514 para no
           requerir permisos de administrador.
   L15-16  DEFAULT_OPERATOR: nombre que firma las acciones en la auditoría
           mientras el MVP no tenga inicio de sesión (Corte 3).


--------------------------------------------------------------------------------
 5.4 app/config.py  -  Carga de la configuración
--------------------------------------------------------------------------------

  +--- app/config.py ---------------------------------------------------------
  |   1 | """
  |   2 | Configuración de la aplicación.
  |   3 | 
  |   4 | Los valores se leen de variables de entorno (archivo .env, que NUNCA se sube
  |   5 | a GitHub). Si una variable no existe se usa un valor por defecto seguro para
  |   6 | desarrollo local. Ver .env.example.
  |   7 | """
  |   8 | import os
  |   9 | from pathlib import Path
  |  10 | 
  |  11 | from dotenv import load_dotenv
  |  12 | 
  |  13 | # Carpeta raíz del proyecto (un nivel arriba de /app)
  |  14 | BASE_DIR = Path(__file__).resolve().parent.parent
  |  15 | 
  |  16 | # Carga .env si existe (no falla si no está)
  |  17 | load_dotenv(BASE_DIR / ".env")
  |  18 | 
  |  19 | 
  |  20 | class Config:
  |  21 |     # Clave para sesiones de Flask. En desarrollo se genera una aleatoria
  |  22 |     # si no se define; nunca se escribe una clave fija en el código.
  |  23 |     SECRET_KEY = os.getenv("SECRET_KEY") or os.urandom(32).hex()
  |  24 | 
  |  25 |     # Ruta del archivo SQLite
  |  26 |     DATABASE_PATH = Path(os.getenv("DATABASE_PATH", BASE_DIR / "data" / "noc.db"))
  |  27 | 
  |  28 |     # Receptor Syslog UDP. Se usa 5514 porque el puerto estándar 514
  |  29 |     # requiere permisos de administrador.
  |  30 |     SYSLOG_HOST = os.getenv("SYSLOG_HOST", "127.0.0.1")
  |  31 |     SYSLOG_PORT = int(os.getenv("SYSLOG_PORT", "5514"))
  |  32 | 
  |  33 |     # Nombre del operador por defecto (para auditoría en el MVP sin login)
  |  34 |     DEFAULT_OPERATOR = os.getenv("DEFAULT_OPERATOR", "operador_noc")
  +-----------------------------------------------------------------------------

 EXPLICACIÓN
   L1-7    Docstring: describe el propósito del archivo.
   L8-11   Importaciones: "os" para leer variables de entorno, "Path" para
           manejar rutas de forma independiente del sistema operativo y
           "load_dotenv" para leer el archivo .env.
   L14     BASE_DIR = raíz del proyecto. __file__ es la ruta de config.py;
           .resolve() la vuelve absoluta; .parent.parent sube dos niveles
           (config.py -> app/ -> raíz).
   L17     Carga el .env de la raíz. Si no existe, no falla: usa los valores
           por defecto.
   L20     Clase Config: agrupa toda la configuración en un solo lugar.
   L23     SECRET_KEY: si no está definida en .env, se genera una aleatoria

 EXPLICACIÓN GENERAL
   - "CREATE TABLE IF NOT EXISTS": crea la tabla solo si no existe. Por eso
     init-db se puede ejecutar varias veces sin borrar datos.
   - "CHECK (...)": regla que la base de datos hace cumplir. Si se intenta
     guardar un valor inválido (por ejemplo, severidad 9), SQLite lo rechaza
     aunque el código tenga un error. Es validación en la capa más baja.
   - "REFERENCES tabla(id)": clave foránea; relaciona tablas.
   - "ON DELETE SET NULL / CASCADE": qué pasa si se borra el registro padre.
   - "INDEX": acelera las búsquedas por esa columna (filtros del dashboard).

 L12  PRAGMA foreign_keys = ON: SQLite trae las claves foráneas apagadas
      por defecto; esta línea las activa.

 TABLA 1 - severities (L18-24): catálogo de severidades de la RFC 5424.
   code 0-7 (CHECK lo garantiza), keyword (emerg, alert...), name,
   description y creates_incident: la POLÍTICA de qué severidades generan
   incidente automático (1 = sí). Tenerla en datos y no en el código
   permite cambiar la política sin reprogramar.

 TABLA 2 - devices (L31-45): inventario.
   name e ip son UNIQUE (no se repiten). vendor solo acepta Cisco,
   Fortinet, Huawei u Otro. status solo acepta 5 estados.
   authorized (L41): LISTA PERMITIDA DE FUENTES. Solo los equipos con
   authorized = 1 son fuentes de confianza para generar incidentes.
   is_simulated (L42): marca los datos de prueba (exigido por el curso).
   created_at / updated_at: trazabilidad de cambios.

 TABLA 3 - syslog_events (L52-71): eventos recibidos.
   received_at (cuándo llegó al NOC) vs event_time (la fecha que trae el
   propio mensaje): pueden diferir si el reloj del equipo está mal; por eso
   NTP es un control obligatorio.
   device_id: equipo del inventario al que se asocia (por IP).
   facility 0-23 y severity 0-7: se calculan del PRI del mensaje.
   raw (L65): el mensaje ORIGINAL, tal cual llegó. Es DATO NO CONFIABLE:
   nunca se interpreta como instrucción ni se ejecuta (defensa contra
   prompt injection).
   origin: udp, importacion o simulador (trazabilidad del origen).
   authorized_source: si la IP de origen está en la lista permitida.
   fingerprint y dup_count: deduplicación. Mensajes idénticos se agrupan
   con un contador en lugar de llenar la base (control de tormentas).
   L73-76 Índices por fecha, severidad, equipo y huella.

 TABLA 4 - incidents (L81-97): ciclo de vida de incidentes.
   status: abierto -> asignado -> en_progreso -> cerrado.
   assigned_to: responsable. resolution: obligatoria al cerrar.
   event_id / device_id: de qué evento y equipo nace el incidente.
   created_by, created_at, updated_at, closed_at: trazabilidad completa.

 TABLA 5 - incident_notes (L100-106): seguimiento.
   Notas con autor y fecha. ON DELETE CASCADE: si se borra el incidente,
   se borran sus notas.

 TABLA 6 - action_proposals (L114-127): FLUJO SEGURO OBLIGATORIO.
   evento -> validación -> PROPUESTA -> revisión humana -> aprobación ->
   ejecución autorizada -> verificación -> auditoría.
   proposed_by: quién propone (asistente_ia u operador).
   status: pendiente -> aprobada/rechazada -> ejecutada -> verificada.
   reviewed_by / reviewed_at: el HUMANO que aprobó o rechazó.
   Un agente de IA solo puede PROPONER; no puede aprobar ni ejecutar.

 TABLA 7 - audit_log (L133-142): auditoría.
   ts, actor, action, entity, entity_id, detail, result (ok, bloqueado,
   error). Política: solo se INSERTA; la aplicación nunca la modifica ni la
   borra. Así queda evidencia de quién hizo qué y cuándo.

 7. CONTROL DE VERSIONES: COMANDOS Y CONCEPTOS DE GIT
================================================================================

 CONCEPTOS
   Repositorio   Carpeta con historial (.git).
   Commit        "Foto" del proyecto en un momento, con mensaje, autor y hash
                 (ej. fb0dc81).
   Rama          Línea de trabajo independiente.
                   main    -> versiones estables y publicadas
                   develop -> trabajo diario; se une a main por Pull Request
   Remoto        Copia en GitHub ("origin").
   Staging       Área de preparación: lo que entrará en el próximo commit.

 COMANDOS USADOS
   git config --global user.name/email   Identidad del autor de los commits
   git init -b main                      Crea el repositorio con rama main
   git commit --allow-empty -m "..."     Commit inicial vacío
   git status                            Estado: qué cambió, qué está preparado
   git remote add origin <url>           Conecta con el repositorio en GitHub
   git push -u origin main               Sube main y recuerda la conexión
   git switch -c develop                 Crea la rama develop y se cambia a ella
   git add <archivos>                    Prepara archivos para el commit
   git commit -m "mensaje"               Crea el commit
   git push                              Sube los commits nuevos
   git log --oneline --graph --all       Historial resumido con ramas
   git mv <origen> <destino>             Renombra y registra el cambio
   git rev-parse --show-toplevel         Muestra la raíz del repositorio

 FORMATO DE MENSAJES (Conventional Commits)
   feat:   nueva funcionalidad          fix:   corrección de error
   docs:   documentación                test:  pruebas
   chore:  configuración/mantenimiento  refactor: mejora sin cambiar función

 AUTENTICACIÓN
   Git Credential Manager (incluido en Git para Windows) autorizó el acceso
   mediante OAuth en el navegador. El token queda en el Administrador de
   credenciales de Windows; nunca en el proyecto ni en texto plano.

 11. PREGUNTAS PROBABLES DE SUSTENTACIÓN (CON RESPUESTA)
================================================================================

 P: ¿Por qué un entorno virtual?
 R: Aísla las librerías del proyecto, evita conflictos con otros proyectos
    y, junto con requirements.txt, permite reproducir la instalación.

 P: ¿Por qué el .env no está en GitHub?
 R: Contiene configuración real y secretos (SECRET_KEY). Se publica solo
    .env.example como plantilla. El .gitignore lo garantiza y git status lo
    demostró.

 P: ¿Cómo se calcula la severidad de un mensaje Syslog?
 R: El mensaje empieza con <PRI>. PRI = facility x 8 + severidad.
    Severidad = PRI mod 8; facility = PRI div 8.
    Ejemplo: <187> -> 187 / 8 = 23 (local7), resto 3 (Error).

 P: ¿Por qué SQLite?
 R: Viene con Python, no requiere servidor y guarda todo en un archivo.
    Suficiente para un MVP con un operador. Si crece se puede migrar a
    PostgreSQL con el mismo modelo.

 P: ¿Qué hace un CHECK en la base de datos?
 R: Impone una regla que la propia base valida: por ejemplo, severidad
    entre 0 y 7. Aunque el código tenga un error, el dato inválido no entra.

 P: ¿Qué es "is_simulated" y por qué existe?
 R: Marca cada dato de prueba. El curso exige que lo simulado esté
    identificado y no se presente como real.

 P: ¿Por qué IP 192.0.2.x, 198.51.100.x y 203.0.113.x?
 R: La RFC 5737 las reserva para documentación. No se enrutan en Internet,
    así que no hay riesgo de usar IP reales de producción.

 P: ¿Qué es la auditoría y por qué solo se inserta?
 R: Es el registro de quién hizo qué, cuándo y con qué resultado. Si se
    pudiera modificar o borrar, un atacante (o un agente de IA) podría
    ocultar sus acciones.

 P: ¿Qué es /api/health?
 R: Un endpoint de chequeo de salud: confirma que la aplicación y la base
    de datos responden. Los sistemas de monitoreo lo consultan
    periódicamente.

 P: ¿Por qué 127.0.0.1 y no 0.0.0.0?
 R: 127.0.0.1 solo acepta conexiones del mismo equipo; 0.0.0.0 expondría
    la aplicación a toda la red sin autenticación.

 P: ¿Por qué el puerto 5514 y no el 514?
 R: Los puertos por debajo de 1024 requieren privilegios de administrador.
    En los equipos de red se configura el puerto destino 5514.

 P: ¿Por qué main y develop?
 R: main guarda solo versiones estables (releases). develop recibe el
    trabajo diario y se une a main mediante Pull Request cuando hay una
    versión lista.

 P: ¿Cómo evitan la inyección SQL?
 R: Todas las consultas con datos usan parámetros "?". SQLite trata el
    valor como dato, nunca como parte de la instrucción SQL.
