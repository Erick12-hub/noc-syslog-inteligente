 2. CONCEPTOS NUEVOS
================================================================================


 AUTENTICACIÓN vs AUTORIZACIÓN
   Autenticación = ¿quién eres? (usuario y contraseña).
   Autorización  = ¿qué puedes hacer? (rol). Primero una, luego la otra.

 ROL (RBAC, control de acceso basado en roles)
   Los permisos se dan al ROL, no a cada persona. Cambiar a alguien de
   operador a auditor cambia de golpe todo lo que puede hacer.

 PRINCIPIO DEL MENOR PRIVILEGIO
   Cada rol tiene solo lo que necesita. El auditor revisa, pero no puede
   cambiar nada; así su revisión es independiente.

 SEPARACIÓN DE FUNCIONES
   Quien propone un cambio no puede aprobarlo. Hacen falta dos personas para
   ejecutar una acción sobre la red: evita errores y abusos de una sola.

 HASH DE CONTRASEÑA (scrypt)
   No se guarda la contraseña, sino una huella irreversible con "sal"
   aleatoria. scrypt es lento a propósito (~0,2 s): para el usuario no se
   nota, pero hace muy costoso probar millones de contraseñas robadas.

 BLOQUEO POR INTENTOS (anti fuerza bruta)
   Tras 5 fallos la cuenta se bloquea 15 minutos, incluso con la contraseña
   correcta. El mensaje es el mismo si el usuario no existe: no se revela
   qué usuarios hay (enumeración de usuarios).

 CSRF (Cross-Site Request Forgery)
   Una página maliciosa podría hacer que el navegador del operador, que ya
   tiene sesión, envíe un POST al NOC. Cada página lleva un token secreto
   que la otra página no conoce; sin él, la petición se rechaza (403).

 COOKIE HttpOnly y SameSite=Lax
   HttpOnly: JavaScript no puede leer la cookie de sesión (frena el robo por
   XSS). SameSite=Lax: el navegador no la envía en peticiones POST que
   vienen de otro sitio (segunda barrera contra CSRF).

 FUNCIÓN HASH SHA-256 Y CADENA DE HASHES
   SHA-256 produce una huella de 64 caracteres; cambiar una letra cambia toda
   la huella. En la cadena, cada registro incluye la huella del anterior:
       hash_n = SHA-256( hash_(n-1) | datos_n )
   Modificar un registro rompe su hash; borrarlo deja al siguiente apuntando
   a una huella que ya no existe. Es la misma idea que usa una blockchain.

 TRIGGER
   Regla que la base de datos ejecuta sola ante un evento. Aquí: "ANTES de
   UPDATE o DELETE en audit_log -> abortar". Ni la propia aplicación puede
   modificar la auditoría.

 HASH ANCLA
   El último hash verificado, anotado FUERA de la base (bitácora). Si alguien
   borra el final de la cadena o la recalcula entera, el ancla ya no coincide.

 INTERFAZ REGISTRADA vs INTERFAZ DEL EVENTO
   El inventario dice qué interfaces TIENE el equipo; el evento dice cuál
   REPORTA. Si no coinciden: inventario desactualizado o mensaje fabricado.

 4.5 Auditoría encadenada (app/db.py)
--------------------------------------------------------------------------------


 audit() escribe dentro de BEGIN IMMEDIATE: el receptor UDP y la web usan
 conexiones distintas, y sin ese bloqueo dos registros podrían tomar el
 mismo "hash anterior" y bifurcar la cadena. El separador \x1f entre campos
 evita que ("ab","c") y ("a","bc") den el mismo texto y el mismo hash.

  +--- app/db.py  (cadena, migración, triggers y verificación) ---------------

  | 163 |
  | 164 |
  | 165 | def audit_hash(prev_hash, ts, actor, action, entity, entity_id, detail, result) -> str:
  | 166 |     """SHA-256 de los datos del registro unidos al hash anterior (formato fijo)."""
  | 167 |     fields = [prev_hash, ts, actor, action, entity, entity_id, detail, result]
  | 168 |     # "\x1f" (separador de unidad) evita ambigüedades: ("ab","c") != ("a","bc")
  | 169 |     payload = "\x1f".join("" if f is None else str(f) for f in fields)
  | 170 |     return hashlib.sha256(payload.encode("utf-8")).hexdigest()

  | 173 | def _last_hash(conn) -> str:
  | 174 |     row = conn.execute("SELECT hash FROM audit_log WHERE hash IS NOT NULL ORDER BY id DESC LIMIT 1").fetchone()

  | 178 | def audit(conn, actor, action, entity=None, entity_id=None, detail=None, result="ok"):
  | 179 |     """Agrega un registro ENCADENADO de auditoría. Nunca se modifica ni borra después."""
  | 180 |     # BEGIN IMMEDIATE toma el bloqueo de escritura ANTES de leer el último hash:
  | 181 |     # así el receptor UDP y la web no pueden encadenar dos registros al mismo
  | 182 |     # "anterior" al mismo tiempo (la cadena se bifurcaría).

  | 219 |         CREATE TRIGGER IF NOT EXISTS audit_no_delete BEFORE DELETE ON audit_log

  | 226 |     Recorre TODA la auditoría y recalcula cada hash.
  | 227 |
  | 228 |     Devuelve {"ok", "total", "last_id", "last_hash", "broken_at", "reason"}.
  | 229 |     broken_at = id del primer registro donde la cadena se rompe:

  | 244 |                               r["entity_id"], r["detail"], r["result"])
  | 245 |         if r["hash"] != expected:
  | 246 |             return {"ok": False, "total": total, "broken_at": r["id"], "last_id": last_id, "last_hash": prev,
  | 247 |                     "reason": "registro alterado (su contenido no coincide con su hash)"}
  | 248 |         prev, last_id = r["hash"], r["id"]
  | 249 |     return {"ok": True, "total": total, "broken_at": None, "last_id": last_id, "last_hash": prev, "reason": None}

 6. SEGURIDAD APLICADA EN LA FASE 8
================================================================================


   - Sin usuarios por defecto: el primero se crea por consola.
   - Contraseñas: scrypt con sal; nunca en texto, en la auditoría ni en capturas.
   - Fuerza bruta: bloqueo 5 intentos / 15 min, auditado con resultado alerta.
   - Enumeración: mismo mensaje y mismo tiempo si el usuario no existe.
   - Fijación de sesión: sesión nueva al iniciar; cookie HttpOnly + SameSite=Lax.
   - CSRF: token por sesión en cada POST/PUT/DELETE; rechazos auditados.
   - Redirección abierta: después del login solo se va a rutas internas.
   - Menor privilegio: el auditor no cambia nada; la IA no tiene rol.
   - Separación de funciones: nadie aprueba su propia propuesta.
   - Integridad de la auditoría: triggers + cadena SHA-256 + hash ancla.
   - Interfaces: un mensaje con una interfaz inexistente se marca y se audita.
   - Deduplicación: un evento sospechoso ya no se esconde como repetición.

 LÍMITES DECLARADOS
   - La verificación de la cadena es manual (automática en la Fase 9).
   - El hash no usa clave secreta: con acceso al archivo se podría recalcular
     toda la cadena; lo delata el hash ancla guardado fuera de la base.
   - HTTP en 127.0.0.1: la cookie no lleva Secure (con HTTPS se activa).

 10. PREGUNTAS PROBABLES DE SUSTENTACIÓN (CON RESPUESTA)
================================================================================


 P: ¿Por qué no hay un usuario "admin/admin" por defecto?
 R: Es lo primero que prueba un atacante. El primer usuario se crea por
    consola, en el propio servidor, con una contraseña que cumple la política.

 P: ¿Qué pasa si alguien roba la base de datos?
 R: Las contraseñas no están: solo hashes scrypt con sal, muy costosos de
    romper. Y la auditoría está encadenada: cualquier cambio se detecta.

 P: ¿Por qué el mensaje es igual si el usuario no existe?
 R: Para no revelar qué usuarios existen. También se iguala el tiempo de
    respuesta comparando contra un hash ficticio.

 P: ¿Qué es CSRF y cómo lo evitas?
 R: Que otra página use la sesión abierta del operador para enviar acciones.
    Cada página del NOC lleva un token secreto que se envía en cada cambio;
    la otra página no lo conoce y la petición se rechaza y se audita.

 P: ¿Dónde se definen los permisos?
 R: En un solo lugar, app/auth.py: tabla RULES, prefijos y una regla por
    defecto segura. enforce() se ejecuta antes de cada petición.

 P: ¿Puede el asistente de IA aprobar una acción?
 R: No. No tiene usuario ni rol; solo propone. Aprueba un admin_seguridad
    que no sea quien propuso.

 P: ¿Cómo sabes que nadie modificó la auditoría?
 R: Cada registro guarda el SHA-256 del anterior. Al verificar se recalcula
    toda la cadena; si algo se cambió o borró, se indica en qué registro.
    Además, triggers impiden UPDATE y DELETE incluso a la aplicación.

 P: ¿Y si el atacante borra el último registro?
 R: La cadena restante es válida; por eso se anota el hash ancla fuera de
    la base. Si ya no coincide, hubo un recorte.

 P: ¿Por qué probaste la alteración sobre una copia?
 R: Porque la auditoría real es evidencia; nunca se altera. La copia se hace
    con la API de respaldo de SQLite.

 P: ¿Para qué sirve registrar las interfaces?
 R: Para detectar mensajes que no cuadran con el equipo real: inventario
    desactualizado o un mensaje fabricado. En la Fase 9 se leerán por SSH.

 P: ¿Por qué un FortiGate acepta "port1" y un Cisco no?
 R: Cada fabricante nombra distinto sus interfaces; la validación usa las
    familias de cada uno y normaliza los nombres cortos (Gi0/1).

 11. PREGUNTA DE VALIDACIÓN DEL ESTUDIANTE
================================================================================


 Pregunta:
   El usuario operador1 importa a las 3:00 a. m. un log del SIM-CORE-RTR01
   con la línea "Interface GigabitEthernet0/0/9 changed state to down"; el
   router solo tiene registradas Gi0/0/0, Gi0/0/1 y Gi0/0/2. Al día
   siguiente alguien abre noc.db con otra herramienta y borra el registro de
   auditoría de esa importación.
   1. ¿Qué marca recibe el evento y por qué?
   2. ¿Puede operador1 aprobar una propuesta para revisar esa interfaz?
      ¿Quién sí y por qué?
   3. ¿Cómo se descubre el borrado y qué limitación tiene ese mecanismo?

 Respuesta del estudiante (con sus propias palabras, revisada el 2026-10-19):
   El evento queda guardado (no se rechaza, es evidencia) con la marca
   'interfaz_desconocida', porque SIM-CORE-RTR01 tiene interfaces
   registradas en el inventario y Gi0/0/9 no es una de ellas: puede ser un
   inventario desactualizado o un mensaje fabricado. Queda en la auditoría
   como syslog.sospechoso con resultado alerta y, por ser severidad 3 de una
   fuente autorizada, abre un incidente. operador1 no puede aprobar ninguna
   propuesta porque solo el rol admin_seguridad revisa propuestas; además,
   ni un administrador puede aprobar su propia propuesta (separación de
   funciones), así que debe aprobarla un admin_seguridad distinto de quien
   la propuso. Para borrar el registro, el atacante primero tiene que quitar
   el trigger que impide los DELETE; aun así, al verificar la integridad, la
   cadena SHA-256 aparece rota en el registro siguiente, porque su prev_hash
   apunta a un registro que ya no existe. La limitación es que, si se borra
   el último registro o se recalcula toda la cadena (el hash no usa clave
   secreta), solo se detecta comparando con el hash ancla guardado fuera de
   la base, en la bitácora. En esta versión la verificación es manual; en la
   Fase 9 será automática.
